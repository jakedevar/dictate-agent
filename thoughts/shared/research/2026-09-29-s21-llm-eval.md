# S21 — LLM formatting: evaluation record

Every number below was measured on this machine on 2026-09-29/30 with the
code at the commit this note ships in. Reproduce with `just eval-llm …`
(see `crates/dictate-fmt/examples/eval_llm.rs`). Raw reports were written to
`target/eval/` and `/tmp/s21/` (not committed; they are regenerable). Other
parallel slices were building and testing on the same machine, so GPU/CPU
contention is part of the environment; it shows up as rare tail outliers.

## 1. Setup

- **Corpus** `crates/dictate-fmt/tests/eval/corpus.jsonl`: 268 invented cases
  (the repo is public — nothing is taken from real history). Weighted like
  real use: terminal 149 (coding-agent prompts), browser 26, chat 26, email
  21, document 21, editor 15, other 10. Tags: 63 questions, 30 adversarial
  (7 prompt-injection), 23 slash commands, 21 self-corrections, 31 stutters,
  23 fillers, 17 long / 14 mid-length, 13 email greetings, 6 lists, 4
  vocabulary. 55 cases carry 64 protected spans. Length buckets: 1–10 words
  90, 11–25 143, 26–40 19, 41–70 14, 71+ 2.
- **Mask stress set** `tests/eval/mask_stress.jsonl`: 48 synthetic terminal
  prompts with 2–5 spans each (136 spans), spans at sentence edges, adjacent,
  inside questions.
- **Rubric** (`llm::eval::judge`): a case passes when every protected span
  survives byte for byte, nothing leaks (no `must_not_contain`, no
  preamble/markup/prompt echo), `must_keep` present, retracted `must_drop`
  words gone, canonical-word similarity to `expected` ≥ 0.85, question-mark,
  line-structure and initial capitalization agree. Numbers compare
  canonically ("six" ≡ "6"). The *rules-only baseline* scores the input
  itself on the same rubric.
- **Prompt** `s21.2`: system prompt + 4–6 few-shot turns per (style,
  structure, tone); dictation delimited by `<dictation>…</dictation>` and
  framed as data; `think: false`, temperature 0.1, fixed seed, `num_predict`
  = chars/2.5 + 32, stop on the delimiters.

guarded 12b is still better than no formatting when e4b is missing.

### Budget verdict

- Jake's p50 utterance (17 words): **155 ms p50** — well inside the 400 ms
  LLM budget.
- Jake's p90 utterance (53 words): **445 ms p50 — 11 % over the 400 ms
  budget.** Decode-bound (≈60 output tokens × 6.8 ms). Nothing in the client
  can remove it (see §5); only a faster model can. This is a product
  decision for Jake — accept, or pull and evaluate a smaller model (e.g. a
  2B-class Gemma) with `just eval-llm <model>`.
- Tail: in one 30-rep run a single 53-word request took >1.46 s (GPU
  contention) and hit the scaled timeout — it failed open to the rules
  output, as designed.

## 3. Masking representation

Protected spans are cut off (leading) or replaced by placeholders before the
model sees them, then verified and restored. Three representations were run
on both sets (gemma4:e4b, prompt s21.2):

| style | corpus pass | corpus span rejections | stress pass | stress span rejections |
|---|---|---|---|---|
| `⟦1⟧` brackets | 99.3 % | 0 | 91.7 % | 0 |
| **`<k1/>` XML tag** | 98.9 % | **0** | **100 %** | **0** |
| `ZQX1` letters | 99.3 % | 1 | 100 % | 0 |

All three kept every span *after* validation (100 %); the differences are
in how often a span-damaged output had to be rejected and in formatting
around placeholders (brackets' four stress failures were one template
where a question ending in a placeholder got a period). **Chosen: `<k1/>`**
— zero span rejections over 316 cases, best stress pass rate, and inline XML
placeholder tags are the convention models are trained to carry through
(machine translation), which matters for other models on the ladder.

The observed production failure (`/research_codebase I would like…` →
`Research codebase. I would like…`) cannot recur: a leading run of
protected spans followed by whitespace is **detached** and never sent; the
first word after it keeps its dictated case (`/describe_pr and mention…`,
not `…And mention…`), except the pronoun "I".

## 4. Validators and what tuning them showed

Final set (all must pass; the rejecting one is named in the error):
`empty_output`, `truncated` (hit `num_predict`), `protected_spans` (dropped,
duplicated, reordered, unknown, mangled, or glued to a word), `prompt_echo`,
`preamble` (reply openers and "Note:" lines), `markup` (fences, emphasis,
headings, bullets, tables **and code symbols** `= + * # @ _ {} [] | <> \ ~ ^ & /`
the input lacked), `new_lines` (only where the category allows structure),
`question` (a `?` may not be lost), `span_correction`, `numbers` (only
numbers the dictation licenses, incl. "twenty twenty six" → 2026, ordinals,
"nine am" → 9:00), `novel_words` (verbatim: none; prose: a few function
words, never negations/quantifiers/content), `edit_distance` (deletions cost
0.5, insertions/substitutions 1, bound 0.55 × input words, plus an order
check: kept words must stay in dictated order), `dropped_words`, and
`length_ratio` (0.4–1.35, +16 chars slack).

Findings that changed the design:

1. **Deletion is a meaning change too.** gemma4:12b dropped "…, I think it
   does" and "That's not what I meant," — outputs that pass every insertion
   check. `dropped_words` aligns output to input (preferring the speaker's
   *last* attempt) and allows a deleted word only if it is a filler/
   discourse marker, a function word, a repeat, part of a compound or split,
   a unit absorbed by a number, a vocabulary replacement, a list enumerator
   (when a list was allowed), within a self-correction around its cue
   ("actually", "sorry", "scratch that", "I mean", "A, no, B"), or part of a
   false start that is restarted. A negation may only go as part of a
   correction.
2. **Executing spoken code is leakage.** 12b turned "x plus equals one" into
   `x += 1`; symbols are not words, so the lexical checks missed it until
   the symbol check was added.
3. **Self-correction next to a protected span** (`/create_plan uh actually no
   /research_codebase …`) cannot be resolved safely — the model may not drop a
   span, so "resolving" it would keep both commands. Such a span is masked
   (not detached) and `span_correction` requires the cue to survive; the
   output then either keeps the correction verbatim or falls back.
4. Asymmetric edit costs were needed because "scratch that" legitimately
   deletes half an utterance; the order check then had to be separate
   because cheap deletions let a full reshuffle through.
5. The pass floor for CI was set from these runs (§7).

## 5. Latency engineering

- **Warm-up.** Cold first request: 2.65–2.74 s to load; with the production
  timeout (17 words → 740 ms) it fails open. Warm-up at daemon start and at
  recording start make cold loads rare (`keep_alive = "30m"` default). A
  recording shorter than the ~2.7 s load still falls back once.
- **Prompt-cache priming** after a load pays off: first request after a cold
  load, load-only p50 242 ms (prompt eval 95 ms) vs load + prime p50 167 ms
  (prompt eval 28 ms), n = 5 each. When the model is already resident the
  prefix is still cached (167 vs 171 ms), so priming costs nothing there.
- **Parallel chunks do not help.** The system Ollama serves one request at a
  time (2 concurrent 58-token requests: 398 ms and 791 ms). On a private
  Ollama (`127.0.0.1:11555`, `OLLAMA_NUM_PARALLEL=4`, flash attention on,
  same model files, killed afterwards) a 53-word input: single request p50
  541 ms; 4 chunks sequential 851 ms; 4 chunks with concurrency 3 p50 531 ms
  / p95 701 ms. Decode slows per slot and each slot re-evaluates the prompt,
  so parallel slots buy nothing at this size. Decision: one request up to 90
  words; above that, chunk at sentence boundaries (for per-chunk fail-open
  and the 4 K context), sequentially; skip above 300 words (`too_long`).
- **Flash attention** (private server): prompt eval 138 → 34 ms for the same
  prompt. The system service already runs that fast (23–29 ms), so there is
  nothing to change there.
- **Timeout policy:** `400 + 20 × words` ms, capped at 4 s; the long-input
  pass as a whole shares the same cap.

## 7. CI tier and its floor

`tests/llm_eval_recorded.rs` replays 316 committed replies
(`tests/eval/recordings/gemma4_e4b.jsonl`) by request fingerprint and
reproduces the live run exactly: 99.3 % pass, 100 % spans, 0 leaks. Any
prompt/option/mask/model change is reported as missing recordings. Floor
**96 %**: ~8 cases of headroom below the recording (live runs during tuning
spanned 97.4–99.3 %), so a reviewed rubric change can land but a regression
in a category or a validator that rejects good output wholesale cannot.
Span preservation must be exactly 100 % and leaks exactly 0.
